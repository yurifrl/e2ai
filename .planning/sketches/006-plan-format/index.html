Plan format

A test plan is a markdown file. Humans read and approve it; agents execute it.
How the arm reads this: frontmatter tells the scheduler when to run. Steps tell the Navigator what to do in plain intent. judge: lines are what the Vision Judge verifies. uses: ties steps to the behavior corpus. Nothing here is code — a reviewer approves prose.
apps/bet-client/tests/plans/checkout-flow-v3.mdsource of truth

id: checkout-flow-v3
app: bet-client
title: Checkout flow end-to-end
surfaces: [web, ios-simulator, android-emulator]
trigger: on-deploy          # runs on every deploy of bet-client
---

# Purpose
Build a slip from the match list, compound selections,
confirm, and reach the confirmation screen.
Failures report to the PR — never block.

## Steps
1. Navigate to home. Intent: see the live match list.
   judge: at least 12 live match cards render.
   uses: MATCH-LIVE-BADGE

2. Tap first match, add selection to the slip.
   judge: slip panel opens with odds 2.40.
   uses: SLIP-TOTAL-COMPOUNDS

14. Submit slip with stake R$50.
   judge: confirm stays disabled until totals API
          returns a non-empty odds bundle.
   uses: SLIP-CONFIRM-GUARDS

15. On failure: fresh-session diagnostic.
   judge: record evidence for the analyst.
   # report only — never blocking
what each part becomesruntime contract
frontmatter → scheduler
  app + trigger  → "run on every bet-client deploy"
  surfaces       → one execution per surface

steps → agents
  numbered text  → Navigator's driving instructions
                   (plain intent, agent figures out
                   selectors/taps itself)
  judge:         → Vision Judge's acceptance check
                   against screenshots/frames
  uses:          → assertion anchored in the behavior
                   corpus (human-approved)

on verdict
  pass/fail per step → live HTML report
  new judge patterns → behavior candidates
  changed corpus     → plan flagged CHANGED → approval

Plan format spec

The whole grammar on one page · same contract the Plan Author writes and you approve
frontmatterscheduler reads
id required
Stable unique identifier, semver-suffixed version (checkout-flow-v3). Renaming means a new plan.
app required
Registered app in the arm. Ties the plan to a repo + deploy workflow.
surfaces required
web, ios-simulator, android-emulator. Each surface gets its own execution per run.
trigger required
on-deploy (every deploy) · on-demand · nightly.
pr-filter optional
Run only when the deploy's PR touches matching paths (paths: apps/bet-client/checkout/**).
timeout optional
Per-surface wall-clock budget. Default 10m.
stepsagents read
N. required
Plain-language driving instruction for the Navigator. No selectors, no code — the agent resolves UI itself and screenshots every step.
judge: required on key steps
What the Vision Judge must confirm on the frames. Falsifiable statements, not vibes.
uses: optional
Behavior corpus reference(s). Run fails if the referenced behavior is unverified; corpus changes flag the plan CHANGED.
on-failure: optional
continue (default: stop surface) · diagnose (fresh-session evidence for the analyst) · always report-only.
Lifecycle rules: new or changed plans queue for human approval before their first run. Approved version runs on every matching deploy. Corpus staleness demotes affected plans until re-approved.
